## 3. SQLite → PostgreSQL 迁移可行性分析

### 3.1 现状（已核实）

| 项 | 现状 |
|---|---|
| 建表机制 | `Base.metadata.create_all()`（`app/core/db.py` 的 `init_db()`，启动时幂等建表） |
| Alembic | 包已装（`alembic==1.14.0`），但**无 `alembic.ini`、无 `alembic/versions/`**，即「未初始化」 |
| PG 驱动 | **未安装**：venv 与 `requirements.txt` 均无 `psycopg`/`psycopg2-binary`/`asyncpg` |
| 配置 | `backend/.env` 未设 `DATABASE_URL`，走默认 SQLite |
| 现有数据 | `backend/data/app.db`（约 204 KB）：管理员账号 + 系统默认配置 + 测试产生的任务/素材/草稿 |
| 目标 PG | 127.0.0.1:5432，用户 `postgres`，密码 `123456`（已连通，缺目标库） |

### 3.2 兼容性核查（结论：模型零改动）

逐项核查 `app/models.py`，全部类型在 PostgreSQL 下可直接落地：

| 当前用法 | SQLite | PostgreSQL | 结论 |
|---|---|---|---|
| 字符串主键 `String(40)`（应用生成 `u_/t_/a_` 前缀 ID） | ✅ | ✅ TEXT/VARCHAR | 无自增依赖，直接迁移 |
| `JSON` 列 | ✅ | ✅ JSONB/JSON | SQLAlchemy 自动序列化 |
| `DateTime(timezone=True)` | ✅（存 naive） | ✅（存 tz-aware） | SQLAlchemy 自动转换 |
| `BigInteger` / `SmallInteger` | ✅ | ✅ BIGINT / SMALLINT | 直接对应 |
| 部分唯一索引（`source='task'` 等） | `sqlite_where` | `postgresql_where` | **已双方言声明，无需改** |
| 业务 SQL | 仅 `func.count()` 等通用函数 | ✅ | 无 SQLite 专属函数（无 `strftime` 等） |
| SQLite PRAGMA | `core/db.py` 内 `startswith("sqlite")` 保护 | 自动跳过 | 无影响 |

> 结论：**schema 与模型是「PG 就绪」的**，唯一硬阻塞是「缺驱动 + 缺目标库 + 未改 DATABASE_URL」。

### 3.3 三个阻塞点与解法

| # | 阻塞 | 解法（分析，不执行） |
|---|---|---|
| 1 | 缺 PG 驱动 | 安装 `psycopg[binary]`（推荐，纯 wheel 免编译）并加入 `requirements.txt`；`postgresql+psycopg://` 即指它 |
| 2 | `.env` 未设 `DATABASE_URL` | 写入 `DATABASE_URL=postgresql+psycopg://postgres:123456@127.0.0.1:5432/contenthub` |
| 3 | 缺目标库 | 先建库：`CREATE DATABASE contenthub;`（或改用已有库） |

### 3.4 Alembic 能否实现迁移？

**能，但要区分「结构迁移」与「数据迁移」，且当前项目还没初始化 Alembic。**

| 迁移类型 | Alembic 是否胜任 | 说明 |
|---|---|---|
| **结构迁移（建表）** | ✅ 能 | Alembic 的 `autogenerate` 可从当前模型生成首版 `create_table` 迁移脚本 |
| **数据迁移（搬行）** | ⚠️ 能但非本职 | Alembic 侧重 DDL 版本化；搬数据需在迁移脚本里写 `op.bulk_insert` 或 `op.execute`，或干脆用一次性脚本对拷 |

### 3.5 推荐迁移路径（两步走）

**第一步：结构落地（二选一）**

- **方案 A（最省事，零迁移脚本）**：改 `DATABASE_URL` 指向 PG + 装驱动，应用启动时 `create_all` 自动在 PG 建全表。适合「现有数据不重要或直接放弃 SQLite 数据」的情况。
- **方案 B（推荐，长期正确）**：初始化 Alembic，`alembic init` + 配置 `env.py` 读 `settings.database_url` + `autogenerate` 生成首版迁移 + `alembic upgrade head`。此后所有 schema 变更走 Alembic，摆脱 `create_all`。

**第二步：数据迁移（若需保留现有数据）**

一次性「SQLite → PG」对拷脚本（比 Alembic data migration 更直观）：

```
两个 SQLAlchemy engine：
  source = create_engine("sqlite:///.../app.db")
  target = create_engine("postgresql+psycopg://postgres:123456@127.0.0.1:5432/contenthub")

按外键依赖顺序逐表拷贝（先父后子）：
  users → tasks → task_outputs / assets → task_attachments / drafts / watermark_configs
  → lexicon_keywords → system_settings → service_status（固定 id=1）
```

> 因为主键是应用生成的字符串、JSON/时间由 SQLAlchemy 序列化，对拷**不需要手动做类型转换**，`ORM` 或 `Core insert` 都能直接跑。

### 3.6 迁移风险与注意事项

| 风险 | 说明 | 对策 |
|---|---|---|
| **Alembic 首版基线** | 项目现在是 `create_all`，没有版本历史 | 引入 Alembic 时用 `alembic stamp head` 把现有结构定为基线，避免「历史不一致」 |
| **部分唯一索引** | `create_all` 对 PG 会正确生成 `CREATE UNIQUE INDEX ... WHERE source='task'` | 迁移后抽查索引是否存在 |
| **数据外键顺序** | 直接乱序插入会撞外键 | 严格按 §3.5 父→子顺序 |
| **`service_status` 单行** | 主键固定 `id=1` | 迁移后确认只有一行，避免 seed 重复建 |
| **密码/密钥** | 生产迁移后务必替换 `JWT_SECRET`、填真实 `AI_API_KEY` | 不要带演示密钥上线 |
| **SQLite 数据中的时间** | naive datetime | SQLAlchemy 会补 tz 写入 PG，一般无感 |

## 5. 结论与建议

1. **整体可行**，前后端已基本完工，剩余主要是「数据库换引擎 + 配置生产化」。
2. **SQLite→PG 迁移可行、成本低**：模型与 SQL 已是 PG 就绪，硬阻塞只有「装驱动、建库、改 URL」三件事。
3. **Alembic 推荐引入**（方案 B）：当前 `create_all` 在单机够用，但一旦进入持续演进，Alembic 是必须的 schema 版本化工具；首版基线用 `stamp head` 处理即可。
4. **数据迁移**建议用「双 engine 对拷脚本」而非硬塞进 Alembic，主键自生成 + ORM 序列化让对拷几乎零转换成本。

> 本报告为纯分析。下一步（安装驱动、初始化 Alembic、写迁移脚本、执行迁移）需你确认后再进入实施阶段。

## 6. 补充：Alembic 现状说明与 MySQL / PostgreSQL 方案对比

### 6.1 「requirements 里有 alembic，但项目没配置」是什么意思

`requirements.txt` 只是**依赖声明清单**，写了 `alembic==1.14.0` 只代表「装了这个包」，不代表「项目在用 Alembic 管理数据库」。

一个 Alembic 已接入的项目必须有三样东西，当前项目三样都没有：

| 必需物 | 作用 | 当前状态 |
|---|---|---|
| `alembic.ini` | Alembic 主配置（脚本目录、数据库 URL） | ❌ 不存在 |
| `alembic/env.py` | 迁移运行时环境（连库、导入模型 metadata、配置方言） | ❌ 不存在 |
| `alembic/versions/*.py` | 版本化迁移脚本，一条一个版本 | ❌ 不存在 |

所以现在的真实建表方式仍是 [app/core/db.py](../../重构源码/backend/app/core/db.py) 里的：

```python
Base.metadata.create_all(bind=engine)   # init_db()，启动时执行
```

`create_all` 的行为特点决定了它的局限：

| 行为 | 后果 |
|---|---|
| 只建「缺失的表」 | 新增表 ✅ 生效 |
| 不改「已存在的表」 | **加字段/改类型/删字段一律不生效**（schema 漂移） |
| 没有任何版本记录 | 无法回滚、无法审计、多环境难对齐 |

> 一句话：**包买了，但没接线。** 单机开发够用；一旦 schema 要演进，就必须接 Alembic。

### 6.2 配置难度评估

| 场景 | 难度 | 预估耗时 |
|---|---|---|
| 只接管「新库」（放弃旧数据） | ★☆☆☆☆ | 15~30 分钟 |
| 接管「已有旧库」并补版本历史 | ★★☆☆☆ | 30~60 分钟 |

核心步骤（4 步）：

1. `alembic init alembic` —— 生成 `alembic.ini` + `alembic/env.py` + `versions/`。
2. 改 `env.py`：`from app.core.config import settings` 读 `database_url`；`from app.models import Base` 取 `target_metadata = Base.metadata`；`sys.path` 补上 backend 根目录。
3. `alembic revision --autogenerate -m "init schema"` —— 从模型生成首版建表脚本。
4. `alembic upgrade head` —— 在目标库执行。

**已有旧库时**多一步：先 `alembic stamp head` 把「当前结构」标记为基线，避免 autogenerate 生成一份「表已存在」的重复迁移。

已知坑（都可以提前规避）：

| 坑 | 规避 |
|---|---|
| `alembic.ini` 和 `.env` 两处写 URL，容易不一致 | `alembic.ini` 留空，`env.py` 统一从 `settings` 读 |
| 目标库已由 `create_all` 建过表 | 用 `stamp head` 定基线，或换空库 |
| 以后若还要兼容 SQLite | `env.py` 里 `render_as_batch=True`（SQLite 不支持多数 ALTER） |
| 部分唯一索引（`WHERE source='task'`） | 确认目标库方言是否支持（见 6.3） |

### 6.3 MySQL 与 PostgreSQL 迁移成本对比

**结论：整体规模相同，都是「装驱动 + 建库 + 改 URL +（可选）Alembic +（可选）数据对拷」；MySQL 多 1 个真实风险点（部分唯一索引），其余是细节差异。**

| 维度 | PostgreSQL | MySQL | 差异 |
|---|---|---|---|
| 驱动 | `psycopg[binary]`（纯 wheel） | `pymysql`（纯 Python）或 `mysqlclient`（需编译） | 同量级 |
| URL | `postgresql+psycopg://...` | `mysql+pymysql://...?charset=utf8mb4` | 一行 |
| 建库 | `CREATE DATABASE contenthub;` | `CREATE DATABASE contenthub CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;` | MySQL 必须显式指定字符集 |
| JSON 列 | `JSONB` 原生 | MySQL 5.7.8+ / 8.0 原生 JSON | 均可 |
| 时区 | `TIMESTAMPTZ` 保留时区 | `DATETIME` **不存时区**，读回是 naive | MySQL 需依赖 `schemas.py` 的 naive→UTC 兜底（已存在） |
| 部分唯一索引 | ✅ 完整支持（`postgresql_where` 已在 models 声明） | ❌ **不支持**，方言参数被忽略 → 退化为整列唯一 | **唯一实质差异** |
| 自增/主键 | 字符串主键，无差异 | 同 | 无 |
| 保留字 | `key` 等 | `key` 在 MySQL 是保留字，SQLAlchemy 会自动加反引号 | 需回归验证一次 |

**关于「部分唯一索引」的实际影响**（`models.py` 两处）：

```python
Index("uq_assets_task_output", "source_task_id", unique=True,
      sqlite_where=text("source = 'task'"),
      postgresql_where=text("source = 'task'"))
```

- PG：唯一约束只作用于 `source='task'` 的行，语义严格。
- MySQL：`WHERE` 被丢弃，变成「`source_task_id` 整列唯一」。
- 因为上传素材的 `source_task_id` 为 `NULL`，而 MySQL 唯一索引**允许多个 NULL**，所以**功能上大概率仍能跑**；只是「同一任务 ID 出现在非 task 来源」时会被误拦。若业务上不存在该情况，可不处理；否则需在应用层校验或改用生成列。

**成本结论**：

| 选择 | 适配改动 | 风险 |
|---|---|---|
| PostgreSQL | models 已 PG 就绪，**零改动** | 低 |
| MySQL | 需确认部分唯一索引降级可接受；建库字符集；回归一次中文/emoji | 中低 |

> 两者工作量差距在 **0.5 人日以内**。若追求「零模型改动 + 语义严格」，PG 更省心；若团队运维栈统一在 MySQL，MySQL 也可行，代价是接受部分唯一索引降级。

### 6.4 目标库选择对文档的影响

若最终选 MySQL，需同步修改 `04-数据库设计文档.md` 中的类型映射（`UUID`/`TIMESTAMPTZ`/`JSONB` → `VARCHAR(40)`/`DATETIME`/`JSON`）与索引说明；`02-系统架构设计文档.md` 的「PostgreSQL 15」也需改为 MySQL 8.0。当前两份文档仍按 PostgreSQL 编写。
