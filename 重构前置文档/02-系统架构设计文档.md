### 1.2 关键设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 前端框架 | React 18 + TypeScript + Vite | 与 Demo 同源，工程化优于纯 JSX |
| 后端框架 | FastAPI + Uvicorn | 与原有 Python 逻辑（watermark/ai_gen/lexicon）可平滑迁移 |
| 数据访问 | SQLAlchemy 2.0 + Alembic | ORM + 迁移脚本化，替代飞书表 |
| 任务队列 | Redis + ARQ（或 Celery） | 解耦「提交」与「处理」，替代 worker 轮询 |
| 数据库 | PostgreSQL 15 | 主业务库；结构稳定、事务完整 |
| 缓存/队列 | Redis 7 | 任务队列、限流、会话/热点缓存 |
| 文件存储 | 本地磁盘（可切 MinIO/S3） | 通过 storage 抽象层解耦，小规模先落盘 |
| 认证 | JWT（access + refresh） | 无状态，适配 SPA |
| 视频处理 | ffmpeg（子进程） | 沿用已验证的提取版 ffmpeg |
| 实时进度 | SSE（Server-Sent Events） | 任务进度单向推送够用，避免 WebSocket 复杂度 |
| AI 调用 | httpx（异步） | 替换原 urllib，支持并发 |
| **本地视频导入** | 浏览器 `File` + `URL.createObjectURL`，会话内引用 | 用户挑片阶段不产生任何服务端流量；确认要留存的成品才真正上传，避免「传 2GB 又放弃」 |
| **草稿存储** | 草稿序列化为 Markdown 写入 `assets`（`source=draft`） | 复用素材库的检索/下载/权限，不为草稿另建一套存储与页面 |

### 1.3 本地导入的职责边界

```
┌────────────── 浏览器（前端）──────────────┐        ┌──────── 服务端 ────────┐
│ input[type=file] / 拖拽                   │        │                        │
│   → File 对象（不上传）                    │        │                        │
│   → objectURL 喂给 <video>                │        │                        │
│   → 读 metadata（duration/width/height）  │        │                        │
│   → 叠加水印做实时预览（DOM 绝对定位）       │        │                        │
│                                           │        │                        │
│ 点「保存到素材库」                          │        │                        │
│   → 先 POST /assets/upload（源视频入库）    │───────▶│ 落盘 + 建 assets 记录    │
│   → 再 POST /tasks(type=video, asset_id)  │───────▶│ 入队                    │
│                                           │        │ worker: ffmpeg 渲染     │
│   ← SSE / 轮询拿到 progress               │◀───────│ 回写进度                │
│   ← done 后成品 asset 出现在素材库          │◀───────│ 产物回写 assets(source=task) │
└───────────────────────────────────────────┘        └────────────────────────┘
```

**约定**：

- 前端只做「读取 + 预览」，**不做**编码；渲染一律在 worker。
- 本地导入的文件在「保存到素材库」时才上传；如果用户直接关页面，服务端零残留。
- 预览用的水印是 DOM 叠加（近似效果），最终以 worker 输出为准；两者差异需在 UI 注明「预览为效果示意」。
- 服务端不信任前端上报的 `duration/resolution`，worker 用 ffprobe 复算并以此为准。

## 2. 后端设计

### 2.1 分层结构

```
backend/app/
├── api/           # 路由层：仅做参数校验、鉴权、调用服务层、组装响应
├── core/          # 配置、安全、依赖注入、异常处理
├── models/        # SQLAlchemy ORM 模型（与数据库设计一一对应）
├── schemas/       # Pydantic 请求/响应模型（与 API 契约一一对应）
├── services/      # 业务逻辑（水印、AI 生成、词库、存储、任务编排）
├── workers/       # 后台异步任务（消费 Redis 队列）
└── db/            # 会话管理、迁移
```

**依赖方向**：`api → services → models/db`，`api` 不直接碰 ORM，`services` 不依赖 Web 层。

### 2.2 服务层模块

| 模块 | 职责 | 迁移自 |
|---|---|---|
| `services/watermark.py` | 组装 ffmpeg 命令、生成单帧预览图、执行水印 | `watermark.py` |
| `services/ai_generator.py` | 多厂商抽象：文案生成 / 生图提示词 / 生图 | `ai_gen.py` |
| `services/lexicon.py` | 词库查询（plan）、采集（ensure）、覆盖块构建 | `lexicon.py` |
| `services/storage.py` | 文件上传/下载/删除/缩略图，本地/对象存储切换 | 新增 |
| `services/task_service.py` | 任务创建、状态机、认领、超时回收、重试/取消 | `worker.py` 的调度逻辑 |
| `services/auth.py` | 登录、Token、密码、权限 | 新增 |
| `services/system_config.py` | 系统配置读写（替代 config.json，热加载） | 新增 |
| `services/draft_service.py` | 把文章/提示词草稿序列化为 Markdown、写入 `assets(source=draft)`，处理「同名更新」 | 新增（v1.1） |
| `services/asset_materializer.py` | 任务产物落库：写存储 → 建 `assets` 记录 → 关联 `task_attachments` | 新增（v1.1） |

### 2.3 AI 生成器设计

沿用原 `ai_gen.py` 的**能力模型**，每个 provider 声明 `supports_vision / supports_image`：

```python
PROVIDERS = {
  "zhipu":      {"base_url": "https://open.bigmodel.cn/api/paas/v4", "vision_model": "glm-4v-flash", "image_model": "cogview-3", "supports_vision": True,  "supports_image": True},
  "dashscope":  {"base_url": "https://dashscope.aliyuncs.com/compatible-mode/v1", "vision_model": "qwen-vl-max", "image_model": "wanx-v1", "supports_vision": True, "supports_image": True},
  "openai":     {"base_url": "https://api.openai.com/v1", "vision_model": "gpt-4o", "image_model": "dall-e-3", "supports_vision": True, "supports_image": True},
  "deepseek":   {"base_url": "https://api.deepseek.com/v1", "vision_model": "deepseek-flash", "image_model": "", "supports_vision": True, "supports_image": False},
  "openai_compatible": {"base_url": "", "supports_vision": False, "supports_image": False},  # 自定义，必填 base_url
}
```

**关键规则**（沿用并固化）：
- 文案模型与生图模型**完全独立**（可不同厂商、不同 Key）。
- 不显式指定能力时跟随 provider 预设，避免「换成纯文本模型却因读图/生图失败」。
- 推理模型（DeepSeek 等）正文为空需给出「调大 max_tokens」的明确提示。
- 生图失败可降级（`allow_image_failure`），文案不因配图失败而判死。
- 系统提示词支持「内联 + 外部文件列表」组合加载。

### 2.4 任务处理设计（替代 worker 轮询）

```
用户提交任务
   → FastAPI 写入 DB（status=待处理）
   → 投递到 Redis 队列（按类型分两个队列：video / text）
   → Worker 消费：
        1. 原子认领（UPDATE ... WHERE status=待处理，写 node + started_at）
        2. 执行处理（视频走 ffmpeg，文本走 AI），期间持续回写 progress（0~1）
        3. 【v1.1】产物落库：成品写入存储 → 建 assets 记录（source=task，source_task_id=本任务）
           → 建 task_attachments(role=output_video)
        4. 成功回写结果 + status=已完成；失败回写 error + status=失败（按 max_retry 重试）
   → 前端通过 SSE 订阅任务状态推送，或 3s 轮询兜底
```

**进度回写（v1.1 明确）**：

| 任务类型 | 进度来源 | 回写频率 |
|---|---|---|
| video | `ffmpeg -progress pipe:1` 的 `out_time_ms / 总时长` | ≤ 2s 一次，写 Redis + 每 5s 落库一次（避免高频写） |
| article / prompt | 无可用进度，仅状态流转 | 状态变更时写 |
| 草稿保存 | 同步接口，不走队列 | — |

**失败与重试的产物处理**：

- 第 3 步之前失败 → 无产物，`task_outputs` 不写。
- 第 3 步写入存储成功、写库失败 → 由清理任务按 `storage_key` 回收孤儿文件（幂等键：`task_id + output`）。
- 重试时不复用上一次的半成品，重新生成并以新 `storage_key` 覆盖。

**并发模型**（沿用原设计的分池思路）：
- 视频队列：CPU 密集，并发 2（可配）。
- 文本队列：等模型接口，并发 4（可配）。
- 两个池独立消费，互不阻塞。

**可靠性与一致性**：
- **认领锁**：用数据库原子更新（`UPDATE tasks SET status='processing', node=... WHERE id=? AND status='pending'`）保证同一条任务只被一个 worker 认领。
- **超时回收**：`status=处理中` 且 `start_time` 超过 `claim_timeout`（默认 30min）的任务，被定时任务重新置为待处理。
- **幂等**：worker 崩了重启后，未完成的任务要么回滚到待处理，要么靠超时回收。

### 2.5 权限模型（RBAC）

**三层拦截**：

| 层 | 实现 | 作用 |
|---|---|---|
| 路由层 | 前端路由表 `meta.roles`，无权限直接重定向 | 不让人进入空白页 |
| 接口层 | FastAPI 依赖 `require_role("super","admin")` | 真正的安全边界 |
| 数据层 | `scope_all=false` 时按 `created_by` 过滤查询 | 横切到列表/详情/下载 |

**角色能力矩阵（v1.1）**：

| 资源 | super | admin | editor | viewer |
|---|:---:|:---:|:---:|:---:|
| `/users/*`（成员管理） | ✅ | ✅ | ❌ | ❌ |
| `/system/settings`（全部配置） | ✅ | ✅ | ❌ | ❌ |
| `/system/status` | ✅ | ✅ | ❌ | ❌ |
| `/watermark/configs`（方案 CRUD） | ✅ | ✅ | ✅ | ❌ |
| `/assets/upload`、`/assets/import` | ✅ | ✅ | ✅ | ❌ |
| `/articles/drafts`、`/prompts/drafts` | ✅ | ✅ | ✅（仅自己） | ❌ |

**v1.1 变更说明**：`/system/*` 从「仅 super」改为「super + admin」。理由：

1. 实际运维中改 AI Key、调并发、换存储路径的频率远高于账号级操作，如果只有超管能做，会长期阻塞；
2. 超管账号是唯一账号（`super` 不可新增），一旦持有人不在，配置就无法变更是单点风险；
3. `super` 仍保留账号所有权（创建/接管 admin 账号）与审计导出，作为「最后一道闸」。

**实现要点**：

```python
# core/deps.py
def require_role(*roles: str):
    def _dep(user: User = Depends(get_current_user)) -> User:
        if user.role not in roles:
            raise HTTPException(403, detail={"code": "FORBIDDEN"})
        return user
    return _dep

# api/v1/system.py
@router.patch("/settings", dependencies=[Depends(require_role("super", "admin"))])
async def update_settings(...): ...
```

## 4. 关键数据流

### 4.1 视频水印链路（v1.1：本地导入 → 保存到素材库 → 下载）

```
【阶段 A：导入（纯前端）】
用户点击「导入视频」或拖拽
  → <input type=file accept="video/mp4,video/quicktime,...">
  → 校验扩展名白名单 + 大小 ≤ 2GB
  → URL.createObjectURL(file) → <video src=...>
  → loadedmetadata 读 duration / videoWidth / videoHeight
  → 呈现素材信息（文件名/格式/分辨率/时长/大小），标记「本地文件 · 未入库」

【阶段 B：配置与预览】
右侧面板改水印参数 → DOM 层实时叠加（文字/Logo 位置、字号、透明度、边距）
  → 可选「抽帧预览」：POST /watermark/preview（上传当前帧 + 参数）→ 返回带水印单帧 JPEG

【阶段 C：保存到素材库】
POST /assets/upload（源视频，直传或分块）→ 得到 asset_id
  → POST /tasks { type: "video", asset_id, watermark_config, save_to_assets: true }
  → 前端跳转任务中心，任务卡显示「待处理 → 处理中 42% → 已完成」

【阶段 D：worker 渲染与产物落库】
worker 认领 → ffprobe 复算元信息 → ffmpeg 加水印（-progress 回写进度）
  → 成品写入存储 storage_key
  → INSERT assets(source=task, source_task_id=本任务, folder=产物/视频)
  → INSERT task_outputs(output_asset_id) + task_attachments(role=output_video)
  → tasks.status=done, progress=1

【阶段 E：取用】
任务详情「下载成品」→ GET /assets/{output_asset_id}/download
素材库「视频」分类出现该成品，来源徽标「任务产出」，可直接下载 / 再次作为源视频引用
```

> 与 v1.0 的差异：v1.0 只有「提交处理 → 下载」，产出物不进素材库；v1.1 强制走「素材」这一统一实体，保证「任务产物 == 素材库条目」，避免两套文件管理。

### 4.2 文章编写与草稿链路

```
前端填需求 + 关键词 + 参考图
  → POST /tasks（type=article）→ 建任务 + 入 text 队列
  → Worker：词库 plan（快）→ 组装系统提示词 + 覆盖块 → AI 生成文章 → 回写结果
  → 前端展示文章，进入在线编辑

【保存草稿】
点「保存草稿」
  → POST /articles/drafts（首次）或 PUT /articles/drafts/{id}（再次）
  → 服务端把结构化内容序列化为 Markdown：
      front-matter（platform / content_type / audience / keyword / created_at）
      + 标题 + 正文 + 标签 + 合规自检 + 搜索覆盖表
  → 写入存储 media/drafts/{yyyy}/{mm}/{draft_id}.md
  → upsert assets(source=draft, ref_id=draft_id, type=document, ext=MD, folder=草稿/文章)
  → 返回 { draft, asset_id }
  → 前端显示「已保存到素材库 · 刚刚」+「去素材库查看」
```

**同名更新策略**：`article_drafts.id` 是唯一键，草稿每次保存只更新 `body/updated_at` 与该草稿绑定的同一个 `asset`（覆盖 `storage_key` 内容、刷新 `size_bytes`），因此素材库里不会出现一堆同名副本。

### 4.3 生图提示词与草稿链路

```
POST /tasks（type=prompt）→ text 队列 → AI 扩写四节 → 回写结果
【保存草稿】POST /prompts/drafts → 序列化为 md（四节 + 需求原文）
  → assets(source=draft, folder=草稿/提示词, ext=MD)
```

### 4.4 认证与权限链路

```
POST /auth/login（用户名+密码）→ 校验 → 返回 access_token + refresh_token
前端存 Token → 每次请求带 Authorization: Bearer <access>
access 过期 → 用 refresh 换新 → 失败则跳登录
路由守卫读取 user.role → 无权限路由重定向 + Toast 提示
后端每个受限接口挂 require_role(...)，越权返回 403 FORBIDDEN
```

## 7. 非功能性设计要点

- **热配置**：系统设置变更写入 DB，Worker 通过「版本号 + 定时刷新」或发布订阅感知，无需重启。
- **大文件上传**：前端分块上传（chunked upload），后端合并；单文件上限可配（默认视频 2GB、其他 500MB）。
- **本地导入**：导入阶段零服务端流量，只在「保存到素材库」时上传一次源视频；产物由 worker 直接落存储，不回传浏览器。
- **缩略图**：视频首帧 / 图片压缩由 worker 异步生成，避免阻塞请求。
- **限流与配额**：登录接口限流；上传大小/并发按角色配额。
- **可观测性**：统一结构化日志（request_id 贯穿）、任务耗时埋点、`/health` 健康检查。
- **安全**：CORS 白名单、CSRF 无关（Bearer Token）、文件类型白名单 + MIME 校验、路径穿越防护。
